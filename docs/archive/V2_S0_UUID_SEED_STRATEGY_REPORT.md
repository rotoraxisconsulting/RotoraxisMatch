# V2-S0 UUID / Seed Strategy Report

**Date:** 2026-05-29  
**Audit finding:** C3 — Local demo IDs are not Supabase UUIDs. The migration must start clean and must not replay local demo data into Supabase.  
**Status:** Resolved via documentation, code annotations, and admin bootstrap template. No seed data was modified.

---

## 1. Problem Summary

The local demo uses human-readable IDs (`tech-001`, `comp-001`, `prof-t001`, `offer-001`, `oreq-001`, `oapp-001`, `room-seed-001`, etc.) for all primary and foreign keys in `src/data/seeds/*.json`.

Supabase requires UUID primary keys for all domain tables, and `profiles.id` must equal `auth.users.id` (the UUID generated by Supabase Auth).

**Risk without this fix:** A developer unfamiliar with the separation might attempt to insert local demo seeds directly into Supabase, causing constraint errors, or might assume the local seeds represent the Supabase seed baseline.

## 4. Final ID Strategy Rules

### Local demo (AsyncStorage mode)

| Rule | Detail |
|------|--------|
| ID format | Human-readable strings: `tech-001`, `comp-001`, `prof-t001`, `offer-001`, `oreq-001`, `oapp-001`, `room-seed-001`, `msg-seed-001`, `act-001`, etc. |
| Purpose | Readability during local development and QA |
| Loaded by | `src/storage/localDatabase.ts` into AsyncStorage |
| Validated by | `scripts/validateSeeds.js` (checks FK integrity, status rules, chat room invariants — not UUID format) |
| Must be inserted into Supabase? | **NO** |

### Supabase (production mode)

| Rule | Detail |
|------|--------|
| ID format | Real UUIDs generated by Postgres (`gen_random_uuid()`) |
| `profiles.id` | Must equal `auth.users.id` — set by Supabase Auth on registration |
| Seed data | Catalog tables only (5 tables) — no marketplace rows |
| Real user IDs | Come from `auth.uid()` at runtime |
| `DEMO_*` constants | Replaced with real `auth.uid()` session values during migration |

## 6. Supabase Clean-Start Procedure

The first Supabase deployment must follow this order:

1. Run `docs/SUPABASE_SCHEMA_V2.sql` — creates enums, all domain tables, and catalog data
2. Run `docs/V2_S1_ADMIN_BOOTSTRAP_SQL.sql` — inserts first admin profile (after creating auth user in Dashboard)
3. Apply RLS policies from `docs/RLS_PLAN_V2.md`
4. Register real users via Supabase Auth — IDs come from `auth.uid()`
5. Remove `DEMO_*` constants and replace with real session context

**Do NOT** insert any rows from `src/data/seeds/*.json` into Supabase.

| Risk | Mitigation |

| Developer inserts demo seeds into Supabase manually | Header comments in `localDatabase.ts`, `validateSeeds.js`, `SUPABASE_SCHEMA_V2.sql`, and docs explicitly warn against this |
| `DEMO_*` constants are not replaced during migration | `HANDOFF_SUMMARY.md` and `IMPLEMENTATION_PHASES_V2.md` call this out explicitly; step 4 of migration order covers it |
| Catalog data diverges between local `ts` constants and SQL | `scripts/validateSeeds.js` checks against `locationCities.ts` and `aircraftTypes.ts`; SQL INSERTs are the authoritative source for Supabase |
